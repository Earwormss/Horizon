### [Doom Renderer Compiled into 21B-Parameter Transformer](https://www.reddit.com/r/MachineLearning/comments/1voazhm/i_compiled_dooms_renderer_into_a_21bparameter/) ⭐️ 8.0/10

A developer has compiled the classic Doom rendering algorithm into a 21-billion-parameter transformer checkpoint, using a custom compiler that converts computation graphs into transformer weights without any training. The model, loaded as a standard Hugging Face checkpoint, generates a token sequence of pixel drawing commands that can be mechanically applied to render a frame. The host program to load the checkpoint, generate, and parse the output is just 43 lines of Python, while the computation graph definition is compiled into the transformer itself. Rendering one frame requires a 3,614-token prompt and 53,747 generated tokens, taking just over 40 minutes on an NVIDIA B200 GPU—yielding about 35 frames per day, compared to the original Doom&\#x27;s 35 FPS on a 486. The project includes a write-up, weights on Hugging Face, and source code on GitHub.

reddit · r/MachineLearning · /u/notforrob · Aug 14, 15:50

**「Background」** Transformers are typically trained on vast datasets to learn patterns, but this project instead uses a compiler to directly encode a known algorithm into the model&\#x27;s weights, bypassing training entirely. Doom&\#x27;s renderer is a classic software rasterizer that draws the game&\#x27;s 3D environment into a 2D frame, and porting it into a transformer demonstrates that computation graphs can be represented as neural network parameters.

**「Impact」** This work provides a concrete proof-of-concept that compilers can translate traditional software algorithms into transformer weights, potentially enabling new approaches to model interpretability and algorithmic reasoning, though the extreme computational cost \(35 frames per day on a B200\) limits practical use.

**「Impact」** Linux users who use RustDesk for remote administration of Wayland-based systems will benefit from the ability to establish unattended connections, simplifying management of headless or always-on machines. ### [Google Advances Private AI with Homomorphic Encryption](https://blog.google/security/how-google-is-making-private-ai-practical-with-homomorphic-encryption/) ⭐️ 7.0/10

Google has announced progress in making private AI practical using homomorphic encryption, a technique that allows computations on encrypted data without decrypting it. This development could enable AI inference on sensitive data while preserving privacy, potentially reducing the need to expose raw data to cloud providers. However, the announcement lacks specific technical details, and the practical viability remains uncertain due to significant computational overhead. The move is part of Google&\#x27;s broader efforts to address privacy concerns in AI, though it faces skepticism from experts and users alike.

hackernews · u1hcw9nx · Aug 14, 15:43 · [Discussion](https://news.ycombinator.com/item?id=49300314)

**「Background」** Homomorphic encryption \(HE\) is a cryptographic technique that allows computations to be performed directly on encrypted data without decrypting it first, producing an encrypted result that, when decrypted, matches the result of operations on the plaintext. This property enables &\#x27;private AI inference,&\#x27; where a model can process encrypted user inputs and return encrypted outputs, so the service provider never sees the raw data. Google&\#x27;s HEIR \(Homomorphic Encryption Intermediate Representation\) is an open-source compiler toolchain that converts pre-trained AI models operating on unencrypted data into versions that operate on encrypted inputs, aiming to make this approach more practical.

**「Impact」** If Google&\#x27;s homomorphic encryption approach becomes commercially viable, it could enable privacy-preserving AI inference for regulated industries like healthcare and finance, allowing them to use cloud AI without exposing sensitive data. However, the high computational overhead \(potentially over 1000x\) may limit immediate practical adoption, and the lack of technical specifics makes it difficult to assess real-world performance.

**「Community Discussion」** Commenters expressed skepticism about the practicality of homomorphic encryption due to high overheads, with one noting that such techniques are not commercially viable for inference tasks. Others criticized Google&\#x27;s privacy record, pointing out inconsistencies like the lack of end-to-end encryption in their password manager, and questioned the environmental cost of increased resource usage.

### [Adaptive Verification in vLLM: DSpark Confidence-Scheduled Speculative Decoding](https://vllm.ai/blog/2026-08-14-dspark-adaptive-verification) ⭐️ 8.0/10

rss · vLLM Blog · Aug 14, 00:00

**「Background」** Speculative decoding trades extra compute for fewer decode steps, which is nearly free when the GPU is memory-bound at low batch sizes but becomes costly at high concurrency where draft tokens compete with real tokens. The author explains that a static draft length is suboptimal because acceptance rates decay per position and vary with load, so vLLM needs a dynamic approach.

**「Solution」** DSpark introduces a confidence head that scores each drafted token&\#x27;s survival probability, enabling per-step selection of how many draft tokens to verify. The scheduler computes survival probabilities as a running product and allocates a budget B by taking the global top-B across all requests, maximizing expected tokens per unit of step time using profiled cost tables. This runs on the CPU with one-step-old confidences, while per-request allocation uses current values on the GPU via PyTorch and Triton. To support variable-sized verifications, vLLM integrates varlen decode CUDA graphs, leveraging DeepSeek&\#x27;s varlen indexer kernel. The cost model uses median-profiled dummy steps, enforces monotonicity to handle noise, and includes a sharp jump at the cudagraph boundary that encourages staying within the captured region. Results on DeepSeek-V4-Pro-0813 show adaptive verification maintains benefits up to concurrency 256, staying on the Pareto frontier across the sweep. Limitations include requiring full varlen graph support, no eager mode, LoRA, or pipeline parallelism, and rejection of output logprobs.

**「Takeaway」** The author concludes that confidence-scheduled adaptive verification makes speculative decoding an &\#x27;on-by-default&\#x27; win by eliminating the need to tune draft length per workload, providing both low-latency and high-throughput benefits without prior knowledge of the deployment.
